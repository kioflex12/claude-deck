## TECH-1 — Рефакторинг монолитного index.html

**Проблема.** `index.html` — одно огромное полотно: разметка + весь CSS в `<style>` + вся клиентская логика в одном `<script>` (~1800+ строк). Тяжело читать, править, ревьюить; растёт линейно с каждой фичей.

**Что сделать.**
- Разнести на нормальную структуру: отдельные файлы CSS, JS-модули (ES modules), HTML-шаблон тонкий.
- Выделить компоненты/области: доска (board), карточка (card), вью сессии (session view + composer + rail), палитра (Ctrl K), скиллы, MCP, usage-окно.
- Убрать инлайн-обработчики, дублирование, «магические» куски; общий слой data-fetch (sessions/skills/mcp/usage/build/mr/jira) — в один модуль клиента.
- Сохранить дизайн макета 1-в-1 (тот же визуал), это чисто структурная работа.
- Аналогично прикинуть, не пора ли бить `server.mjs` на модули по доменам (sessions / chat+SDK / integrations TeamCity+GitLab+Jira / static serving).

**Почему отдельно.** Рефакторинг — крупная структурная работа; мешать её с продуктовыми правками = грязные диффы и риск регрессий. Делать отдельным заходом, когда фичевый поток притормозит.

## TECH-2 — Все списки только динамически из Claude (без хардкода)

Инвариант: любой список (скиллы, MCP-инструменты, сессии/задачи) Deck получает **на лету при загрузке** из реального окружения Claude Code, а не зашивает в код. Правка списка не должна требовать редактирования кода.
- Сессии/доска — уже динамические (читаются из `~/.claude/projects/*.jsonl`).
- Скиллы вкладки «Скиллы» и MCP вкладки «MCP» — перевести с захардкоженных `SKILLS`/`MCP_SERVERS` на живые эндпоинты (`/api/skills` уже есть; добавить агрегирующий режим и `/api/mcp`). Палитру Ctrl K — на те же живые данные.

(TECH-2 берётся в ближайшую итерацию; TECH-1 — отдельным заходом.)
